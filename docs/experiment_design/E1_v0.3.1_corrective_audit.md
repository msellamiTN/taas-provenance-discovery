## Why this corrective release was necessary

A code audit of v0.3 found material rule defects:
1. Broad substring matching allowed "staged for commit" to trigger `write`.
2. The generic word "start" caused a Playwright wait operation to be misclassified as a write.
3. "Start a terminal process" was classified as `write` rather than `exec`.
4. An `add` operation such as `add_slide` was not recognized.
5. Explicit HTTP PATCH/PUT/DELETE/GET method descriptions were not handled.
6. Pure computation/formatting was incorrectly assigned the effect class `read`.

Therefore, v0.3 should be retained for audit history but not used as the current candidate output.

## v0.3.1 corrections

- Match only the first operation-name token or leading verb of the first meaningful description sentence; do not match action words anywhere in a sentence.
- Noun occurrences such as "staged for commit" no longer imply a commit operation.
- Generic "start waiting" no longer implies a write.
- Explicit start/launch of a terminal process or executable job maps to `exec`.
- `add` and leading document-protection descriptions are recognized as write candidates.
- Explicit HTTP GET, POST, PUT, PATCH, and DELETE descriptions receive method-specific candidate handling. POST/PUT/PATCH are write candidates; DELETE is delete; GET is read. These remain documentary candidates; endpoint/server behavior is not verified.
- Retrieval candidates receive `read`; pure computation/formatting candidates receive no fabricated `read` effect.
- Egress-only operations remain false candidates under the approved binary construct, with `egress` recorded separately.
- Schema text, parameter prose, and later examples do not trigger operation effects.
